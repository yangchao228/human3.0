# Human3.0 Product Requirements Document

## 1. 文档信息

- 产品名称：Human3.0
- 文档版本：v0.1
- 文档日期：2026-03-11
- 产品定位：一个帮助用户主动管理信息输入、进行 AI 过滤、输出每日认知摘要并沉淀长期知识库的认知主权系统

## 2. 产品背景

README 中定义的核心问题不是信息不足，而是信息过载和注意力失控。现有信息获取方式以推荐算法为中心，用户难以围绕自己的目标持续构建高价值输入。

Human3.0 的目标是把信息消费从“被动刷流”转为“主动构建认知”，形成一条可控的信息处理链路：

`Collect -> Filter -> Think -> Store`

## 3. 产品愿景

帮助用户建立自己的认知操作系统，让用户决定看什么、为什么看、哪些值得沉淀，而不是被平台算法决定输入结构。

## 4. 产品目标

### 4.1 业务目标

1. 建立统一的信息采集入口，替代分散的信息浏览方式。
2. 通过 AI 对内容进行主题识别、价值评分和摘要提炼，降低信息筛选成本。
3. 每日输出一份 5 分钟可读完的 `Daily Brief`，提升高价值内容的到达率。
4. 将高价值内容沉淀到长期知识库，逐步形成可检索的个人思想数据库。

### 4.2 用户目标

1. 不再高频切换 RSS、公众号、GitHub、YouTube 等多个信息源。
2. 每天只看最重要的少量内容。
3. 快速理解一篇内容是否值得读、为什么值得读。
4. 长期积累某一主题下的高质量材料和洞察。

### 4.3 成功指标

1. 用户成功接入至少 10 个信息源。
2. 每日生成一份日报，日报生成成功率 >= 95%。
3. 用户单日实际阅读条目数控制在 5 到 15 条。
4. 被 AI 判定为高价值的内容中，用户点击查看原文率 >= 30%。
5. 被收藏或归档进知识库的内容占已处理内容的比例 >= 10%。

## 5. 目标用户

### 5.1 核心用户

1. 持续关注 AI、科技、创业、生产力工具的人。
2. 有较强学习意愿，但被信息过载困扰的知识工作者。
3. 希望建立个人研究系统、内容素材库或长期知识库的创作者与独立开发者。

### 5.2 非目标用户

1. 以娱乐内容消费为主的泛用户。
2. 希望获得无限推荐流和高刺激内容的平台用户。
3. 不愿维护信息源、主题和偏好配置的轻度用户。

## 6. 核心产品原则

1. 减少输入，放大价值。
2. 默认少而精，而不是全量堆积。
3. AI 只辅助筛选与提炼，不替代用户做最终判断。
4. 日报优先于信息流，结论优先于原文。
5. 沉淀优先于消费，系统必须支持长期可检索和可复用。

## 7. 产品范围

### 7.1 MVP 范围

1. 信息源管理
2. 内容抓取与入库
3. AI 标签、评分、摘要
4. Daily Brief 生成与查看
5. 内容收藏与知识库沉淀
6. 基础搜索与筛选
7. 手动重跑分析任务

### 7.2 暂不纳入 MVP

1. 多用户团队协作
2. 评论、社交分享、点赞互动
3. 复杂推荐算法
4. 浏览器插件
5. 移动端 App
6. 自动写长文或自动发布到外部平台

## 8. 用户场景

### 场景一：搭建高质量输入源

用户配置 10 到 20 个核心来源，覆盖 RSS、GitHub、Newsletter、公众号文章链接或手动录入源，形成稳定输入池。

### 场景二：每日快速掌握重点

用户每天打开 Human3.0，先看当天日报中的“今日最重要”“值得关注”“工具更新”“一个启发”，判断是否需要展开原文。

### 场景三：围绕主题长期积累

用户关注“AI Agent”“认知科学”“个人操作系统”等主题，系统持续将高分内容沉淀到对应知识分类下，便于未来复盘与写作。

### 场景四：减少无效阅读

用户不需要逐条打开所有内容，只需要看 AI 提炼的核心观点、评分和启发，再决定是否阅读原文。

## 9. 产品角色定义

### 9.1 用户角色

1. 普通用户：配置来源、阅读日报、收藏内容、管理知识库。
2. 管理员：维护系统配置、AI 模型参数、抓取任务和分类规则。

### 9.2 系统 Agent 角色

1. Scout Agent：负责抓取信息源内容、标准化字段、去重入库。
2. Analyst Agent：负责主题识别、价值评分、摘要提炼。
3. Editor Agent：负责按模板生成 Daily Brief。

## 10. 用户流程

### 10.1 主流程

1. 用户添加信息源。
2. 系统定时抓取新内容。
3. 系统去重、解析正文、抽取元数据。
4. AI 对内容进行标签识别、评分和摘要。
5. 系统按规则生成当日报。
6. 用户浏览日报，查看原文或收藏内容。
7. 高价值内容进入知识库。

### 10.2 异常流程

1. 抓取失败：记录错误并允许手动重试。
2. 解析失败：保留原始链接和元信息，标记为待处理。
3. AI 分析失败：进入待分析队列，支持后台重跑。
4. 日报生成失败：保留前一步分析结果，允许手动重新生成。

## 11. 功能需求

### 11.1 信息源管理

功能说明：
用户可新增、编辑、启停和删除信息源，并配置来源类型、分类、优先级和抓取频率。

需求点：

1. 支持 RSS 源接入。
2. 支持 GitHub 仓库或 Release/Trending 订阅。
3. 支持 Newsletter 和博客链接订阅。
4. 支持手动录入文章链接。
5. 支持为信息源绑定默认主题标签。
6. 支持启用/禁用单个信息源。

### 11.2 内容采集与标准化

功能说明：
系统周期性抓取内容，统一存储为标准内容对象。

需求点：

1. 抓取标题、摘要、发布时间、作者、来源、原始链接。
2. 提取正文纯文本或结构化正文。
3. 生成内容唯一指纹，避免重复入库。
4. 记录抓取状态、抓取时间和错误原因。

### 11.3 AI 过滤层

功能说明：
系统对新内容执行主题识别、价值评分和摘要提炼。

需求点：

1. 支持预设主题体系，例如 AI Agent、AI 基础设施、认知科学、生产力工具、创业。
2. 输出 1 到 N 个主题标签。
3. 按评分公式生成综合分数：
   `score = 主题相关度 * 0.4 + 信息密度 * 0.3 + 原创性 * 0.2 + 时效性 * 0.1`
4. 按分数区间输出内容等级：
   `9-10 必须读，7-8 建议读，5-6 可选，<5 忽略`
5. 为每条内容生成：
   - 一句话总结
   - 核心观点
   - 关键启发
6. 支持查看 AI 原始分析结果与手动修正标签。

### 11.4 Daily Brief

功能说明：
系统每天自动生成一份日报，作为主消费入口。

需求点：

1. 日报结构至少包含：
   - 今日最重要
   - 值得关注
   - 工具更新
   - 一个启发
2. 支持按日期查看历史日报。
3. 每个日报条目显示标题、评分、摘要、标签、来源和原文链接。
4. 支持导出 Markdown。
5. 支持手动重新生成日报。

### 11.5 知识库

功能说明：
用户可以将内容归档到长期知识库，围绕主题进行持续沉淀。

需求点：

1. 支持手动收藏或自动归档高分内容。
2. 支持按主题、来源、日期筛选知识条目。
3. 支持为知识条目补充个人备注。
4. 支持从知识库回看原文、AI 摘要和启发。

### 11.6 搜索与筛选

功能说明：
用户可快速找到某一主题、某一来源或某一时间范围内的内容。

需求点：

1. 按关键词搜索标题和摘要。
2. 按标签筛选。
3. 按评分区间筛选。
4. 按来源和日期筛选。

### 11.7 后台任务与系统管理

功能说明：
管理员可查看抓取、分析和日报生成任务状态。

需求点：

1. 查看任务执行日志。
2. 手动触发抓取任务。
3. 手动触发分析任务。
4. 手动触发日报生成。
5. 配置 AI 模型、Prompt 模板和评分阈值。

## 14. 技术方案

### 14.1 总体架构

采用前后端分离架构：

1. 前端：Next.js，负责仪表盘、日报、内容流、知识库和系统设置界面。
2. 后端：Python FastAPI，负责数据 API、抓取调度、AI 分析编排和日报生成。
3. 数据库：MVP 建议 SQLite，便于快速启动；生产可平滑迁移到 PostgreSQL。
4. 异步任务：使用 FastAPI 后台任务或 Celery/RQ 作为后续扩展。
5. 定时调度：cron 或 APScheduler。
6. AI 接入：通过统一模型适配层接入 OpenClaw 或兼容 OpenAI API 的模型服务。

### 14.2 前端建议

1. `Next.js App Router`
2. `TypeScript`
3. `Tailwind CSS` 或 `shadcn/ui` 作为基础 UI 方案
4. `SWR` 或 `React Query` 管理数据请求
5. Markdown 渲染用于日报与知识内容展示

### 14.3 后端建议

1. `FastAPI`
2. `SQLAlchemy` 或 `SQLModel`
3. `Pydantic`
4. `APScheduler` 处理定时任务
5. `httpx` / `feedparser` / `BeautifulSoup4` 处理抓取与解析

## 16. 非功能需求

1. 新内容抓取后 5 分钟内完成入库。
2. 单篇内容 AI 分析超时可重试，失败不阻塞整批任务。
3. 日报生成过程可追踪、可重跑。
4. 所有关键任务需要日志和错误状态。
5. 系统需要支持基础鉴权，至少区分普通用户和管理员。
6. 支持中文优先，同时兼容英文内容输入。

## 17. 版本规划

### V1：MVP

1. RSS/博客/GitHub 信息源接入
2. 内容抓取、去重、解析
3. AI 标签、评分、摘要
4. 今日 Brief 与历史 Brief
5. 知识库收藏

1. 手动修正标签与评分
2. 自动归档规则

4. Markdown 导出

### V2：智能化增强

1. 个性化评分权重
2. 多主题视图
3. 周报/月报
4. 用户行为反馈回流优化分析策略

## 18. 风险与约束

1. 信息源解析质量不稳定，不同站点正文抽取成功率会不同。
2. AI 评分和摘要质量受模型能力与 Prompt 设计影响较大。
3. 如果信息源过多，系统会退化成另一个低质量信息流，因此需要产品层限制输入规模。
4. 公众号等封闭平台的数据接入可能存在技术与合规限制，MVP 应优先支持开放链接和 RSS。

## 19. MVP 验收标准

1. 用户可以完成信息源创建，并成功抓取到内容。
2. 新内容可自动完成标签、评分和摘要生成。
3. 系统每天能生成一份结构完整的日报。
4. 用户可从日报进入原文，也可将内容加入知识库。
5. 用户可按标签、来源、日期检索内容。
6. 管理员可在后台看到任务状态并进行重试。

## 20. 一句话定义

Human3.0 不是一个“更多信息”的平台，而是一个“更少但更重要”的认知输入系统。
